# Gestor de Cobros — Contexto del proyecto

Sistema **multi-tenant** de gestión de cobros de cuotas: centraliza distintos negocios (academias deportivas, escuelas de fútbol, centros de cerámica, cualquier rubro que cobre cuotas periódicas a sus alumnos) en una misma instancia, con los datos de cada negocio completamente aislados entre sí.

## Stack

**Backend** (`backend/`):
- NestJS 10, TypeScript
- TypeORM (`typeorm` + `@nestjs/typeorm`) — `synchronize: true` en desarrollo (ver `src/app.module.ts`), sin migraciones formales todavía
- PostgreSQL (local, vía Homebrew)
- Passport (`passport-jwt`, `passport-local`) para auth
- bcrypt para hash de contraseñas
- `class-validator` + `class-transformer` + `ValidationPipe` global (`whitelist`, `forbidNonWhitelisted`, `transform`) en `main.ts`
- Swagger (`@nestjs/swagger`) — `SwaggerModule.setup('api', ...)` en `main.ts`, solo activo si `NODE_ENV !== 'production'`
- CORS habilitado en `main.ts` vía función `origin` (no un array estático) — loguea con `Logger('CORS')` la whitelist completa al bootear y, cada vez que rechaza un origen, un `WARN` con qué origen llegó y contra qué lista lo comparó. Se agregó después de perder tiempo debuggeando a ciegas un error de CORS en Railway (el origen real del frontend desplegado no estaba en `CORS_ORIGINS` del backend — la causa más común de este error no es un bug de CORS en sí, sino una URL de entorno mal sincronizada). La whitelist se sigue leyendo de `.env`/variables de entorno (`CORS_ORIGINS`, coma-separado, con `.trim()` por elemento — un espacio de más después de una coma en la variable de Railway rompía el match exacto contra el header `Origin`) — **en Railway hay que setearla a mano en las variables del servicio del backend**, el `.env` local nunca se despliega (está en `.gitignore`, correctamente).
- **`app.listen(process.env.PORT ?? 3000)`** (antes hardcodeado a `3000`): Railway le asigna un `PORT` a cada servicio y su proxy espera que la app escuche justo ahí — si no coincide, el proxy nunca llega al proceso y devuelve **502 directamente desde su infraestructura**, sin pasar por el `main.ts` de la app en absoluto. Esto es relevante para el punto anterior: un 502 así tampoco trae `Access-Control-Allow-Origin` (porque nuestra app nunca llegó a responder), así que el navegador lo reporta igual como error de CORS — el error de CORS original y el 502 de Postman probablemente eran el mismo problema de fondo. Fallback a `3000` para que el entorno local (sin `PORT` en `.env`) siga arrancando igual.

**Frontend** (`frontend/`):
- Angular 22 (standalone components, signals, sin `NgModule`)
- Tailwind CSS v4 — **ojo**: el config tiene que ser `postcss.config.json` (no `.mjs`), porque el builder de Angular (`@angular/build`) solo reconoce esa extensión para detectar PostCSS custom; sin eso, `@tailwind utilities` queda sin procesar silenciosamente (bug real que se pisó y se corrigió).
- **Conectado al backend real** desde esta etapa: login real + JWT, y Alumnos/Cuotas/Clases sobre `HttpClient`. El flujo de comprobante/revisión (Pagos) sigue mockeado — ver sección Frontend más abajo.

## Multi-tenancy (arquitectura central)

Decisiones tomadas:
- Una sola base de datos compartida, con columna `negocio` (FK a `Negocio`) en cada tabla tenant-scoped: `Usuario` (nullable), `Alumno`/`Cuota`/`Pago` (NOT NULL).
- `Rol` y `Permiso` quedan **globales** (sin `negocioId`, compartidos entre todos los negocios).
- Los `Negocio` se cargaban a mano vía SQL directo — desde esta vuelta existe `POST /negocios` para eso, pero sigue sin haber flujo de alta **self-service** (nadie de afuera puede crear su propio negocio; ver sección Negocios).
- **Sin Postgres Row-Level Security** (decisión explícita, diferido). El único mecanismo de aislamiento es el filtrado por `negocioId` en cada query de cada service — no hay backstop a nivel DB. Esto es lo más frágil del sistema: cualquier query nueva que se olvide el filtro es una fuga de datos entre negocios.

Mecanismo:
- `Negocio` ([negocio.entity.ts](backend/src/negocios/modelo/negocio.entity.ts)): `id`, `nombre`, `descripcion?`, `activo`, `fechaAlta?`, `logoUrl?` (key del bucket, ver más abajo). Ya existe API real para crear uno y para leer/editar el propio (ver sección Negocios).
- `@NegocioId()` ([negocio-id.decorator.ts](backend/src/auth/decorators/negocio-id.decorator.ts)): param decorator que lee `request.user.negocioId` (ya viene en el JWT). Se usa en cada handler de Alumnos/Cuotas/Pagos para pasar el `negocioId` explícito a cada método de servicio — mismo espíritu que `@Roles()`, pero como param decorator para no repetir `@Req()` en ~15 handlers.
- **Patrón repetido en los 3 services** (Alumnos → Cuotas → Pagos): todo método recibe `negocioId` y lo suma al `where`; `crear()` que referencia una entidad padre (ej. `Cuota.alumnoId`) valida existencia **y tenencia cross-tenant en la misma llamada**, usando el `obtenerPorId(id, negocioId)` ya scopeado del servicio padre. `NotFoundException` siempre (nunca `Forbidden`), para no filtrar si algo existe en otro negocio.
- **Ningún DTO de entrada** (`Crear*Dto`/`Actualizar*Dto`/`Filtrar*Dto`) tiene nunca un campo `negocioId` — siempre sale del JWT, jamás del body/query (el `ValidationPipe` con `forbidNonWhitelisted` ya lo rechazaría si alguien lo mandara).
- `AuthService.login()` mete `negocioId: user.negocio.id` en el payload del JWT; si el usuario no tiene negocio asignado, el login falla explícito en vez de emitir un token con `negocioId: undefined`.
- `AuthService.register()` hereda el `negocioId` del ADMIN autenticado que crea el nuevo usuario (nunca del body).
- **Verificado end-to-end** con 2 negocios reales sembrados en la DB (ids 1 y 2, ver más abajo): aislamiento confirmado en listar/obtener/actualizar/eliminar de los 3 recursos, y en la integridad referencial cruzada (no se puede crear una `Cuota` para un alumno de otro negocio, ni un `Pago` sobre una cuota de otro negocio).

## Módulos y entidades

### Alumnos (`backend/src/alumnos/`)

`Alumno` ([alumno.entity.ts](backend/src/alumnos/modelo/alumno.entity.ts)): `id`, `negocio` (`ManyToOne`, NOT NULL), `clase?` (`ManyToOne` a `Clase`, nullable — no todo negocio necesita agrupar por clase), `nombre`, `apellido`, `telefono?`, `email?`, `fechaAlta`, `activo`, `usuario?` (`OneToOne` opcional con `Usuario`, `@JoinColumn` del lado de Alumno), `cuotas` (`OneToMany`).

CRUD completo en [alumnos.service.ts](backend/src/alumnos/servicios/alumnos.service.ts) / [alumnos.controller.ts](backend/src/alumnos/controladores/alumnos.controller.ts). `crear`/`actualizar`/`eliminar` llevan `RolesGuard` + `@Roles('ADMIN')` por método (mismo patrón que Cuotas/Pagos/Clases) — **corregido**: hasta esta vuelta el controller solo tenía `AuthGuard('jwt')` a nivel de clase, así que cualquier cuenta `ALUMNO` podía crear/editar/borrar alumnos vía API aunque la UI nunca se lo ofreciera (hueco descubierto al blindar la navegación del Portal, ver sección Auth y Frontend). `GET` sigue abierto a cualquier autenticado, scopeado por `@AlumnoIdSesion()`. `crear`/`actualizar` validan `claseId` (si viene) contra `ClasesService.obtenerPorId(claseId, negocioId)` — mismo patrón cross-tenant-safe que usa Cuotas para validar `alumnoId`.

**Herencia de cuota al crear un alumno con clase**: si `crear()` recibe `claseId` y esa clase ya tiene una `Cuota` cargada (para cualquiera de sus alumnos), se le clona la más reciente (mayor año/mes) al alumno nuevo — mismo mes/monto/vencimiento, `PENDIENTE` (`CuotasService.crearParaNuevoAlumno`/`obtenerUltimaCuotaDeClase`). Si la clase todavía no tiene ninguna cuota, no se crea nada. Esto introdujo una dependencia circular real entre `AlumnosModule` y `CuotasModule` (antes solo iba en un sentido: Cuotas necesitaba Alumnos para validar el FK; ahora Alumnos también necesita Cuotas para disparar esto) — resuelta con `forwardRef()` en ambos módulos y ambas inyecciones, el mecanismo estándar de Nest para este caso, no una alternativa "más limpia" con eventos (se descartó a propósito, sería el único lugar del proyecto con un patrón de eventos en vez de llamadas directas entre services).

### Clases (`backend/src/clases/`)

`Clase` ([clase.entity.ts](backend/src/clases/modelo/clase.entity.ts)): `id`, `negocio` (NOT NULL), `nombre`, `icono`. Se agregó al conectar el frontend real: el diseño original agrupaba alumnos por "clase" (Fútbol infantil, Torno avanzado, etc.) pero el backend no tenía ningún concepto equivalente — se decidió explícitamente construirlo como entidad real (en vez de dejarlo decorativo o sacarlo de la UI) siguiendo el mismo patrón tenant-scoped que Alumnos/Cuotas/Pagos. CRUD completo en [clases.service.ts](backend/src/clases/servicios/clases.service.ts) / [clases.controller.ts](backend/src/clases/controladores/clases.controller.ts), mismo esquema de permisos que Cuotas (`GET` abierto, mutaciones `ADMIN`). `eliminar()` chequea con `alumnoRepo.count({ where: { clase: { id } } })` que no haya ningún `Alumno` asignado antes de borrar — si hay, tira `BadRequestException` en vez de dejar que la FK explote como un 500 sin manejar.

### Usuarios (`backend/src/usuarios/`)

`Usuario` ([usuario.entity.ts](backend/src/usuarios/modelo/usuario.entity.ts)): `id`, `negocio?` (`ManyToOne`, nullable — se deja abierto por si algún día existe un usuario "superadmin" sin negocio), `email` (único global, no por negocio — ver Decisiones), `password` (hash bcrypt), `nombre?`, `apellido?` (nullable — un `Usuario` de tipo `ALUMNO` no los necesita, esa info ya vive en el `Alumno` vinculado), `fechaAlta`, `fechaModificacion`, `ultimoAcceso`, `alumno` (inverso del `OneToOne`), `roles` (`ManyToMany` con `Rol` vía `@JoinTable` `roles_usuarios`). `UsuarioService.create(email, password, negocioId, nombre?, apellido?)` los persiste si vienen — antes no existían las columnas y `AuthService.register()` los recibía en el DTO y los tiraba (bug documentado en Pendientes, corregido de paso al agregar esto).

`Rol` ([rol.entity.ts](backend/src/usuarios/modelo/rol.entity.ts)): `id`, `nombre` (único), `descripcion`, `permisos` (`ManyToMany` con `Permiso` vía `@JoinTable` `permiso_roles`). **Global**, sin `negocioId`.

`Permiso` ([permiso.entity.ts](backend/src/usuarios/modelo/permiso.entity.ts)): `id`, `nombre` (único), `descripcion`. También global.

> Se evaluó una tabla intermedia explícita (`RolPermiso`) para poder sumarle columnas propias, pero se optó por `@ManyToMany` + `@JoinTable` simple. Si en algún momento hace falta guardar metadata del vínculo (quién asignó qué permiso, desde cuándo), hay que migrar a una entidad explícita — no se puede agregar columnas a una `@JoinTable` implícita.

`UsuarioService` ([usuarios.service.ts](backend/src/usuarios/servicios/usuarios.service.ts)): CRUD básico + `findByEmail` (carga `roles.permisos`, `negocio` y `alumno`, usado por el login), `findByIdWithRelations`, `findByRol`/`findByRolWithoutUser` (⚠️ ver Pendientes), `findByName` (busca `Rol` por nombre), `updateLastLogin` (actualiza `ultimoAcceso`). `create()` tenía un bug real que nunca se había disparado hasta ahora: no seteaba `fechaAlta`/`fechaModificacion`/`ultimoAcceso` (columnas `NOT NULL`) — pasó desapercibido porque los únicos usuarios de prueba hasta esta etapa se habían cargado a mano por SQL, nunca a través de este método. Se descubrió y corrigió al probar el flujo de invitación de alumno (primer camino de código que realmente ejecutaba `create()`).

**Color de acento personalizable (Portal del Alumno)**: `Usuario` suma `colorAccento?: string` (hex, nullable — `null` significa "usar el default de la app"). Primer controller de este módulo, [usuarios.controller.ts](backend/src/usuarios/controladores/usuarios.controller.ts): `GET/PATCH/DELETE /usuarios/mi-color`, todos operando sobre `request.user.sub` (nunca sobre un `:id` de otro usuario — es autoservicio sobre la propia cuenta, sin necesidad de scoping por `negocioId`). `PATCH` valida el formato con `@IsHexColor()` de `class-validator`. Es deliberadamente una preferencia de `Usuario`, no de `Alumno` ni de `Negocio`: es "cómo se ve la app para esta sesión", no un dato del padrón ni una marca institucional (eso ya existe, es el logo de Negocio). Se eligió persistir en el backend (vs. `localStorage`) para que el color viaje con la cuenta sin importar el dispositivo — decisión tomada explícitamente con el usuario.

### Cuotas (`backend/src/cuotas/`)

`Cuota` ([cuota.entity.ts](backend/src/cuotas/modelo/cuota.entity.ts)): `id`, `negocio` (NOT NULL), `alumno` (`ManyToOne`), `mes`, `anio`, `monto`, `estado: EstadoCuota` (enum: `PENDIENTE`, `PAGADA`, `VENCIDA`, `EN_REVISION`), `fechaVencimiento`, `comprobanteUrl?` (nullable — guarda la **key** del objeto en el bucket mientras la cuota está `EN_REVISION`, no una URL pública, ver sección Archivos), `pago` (`OneToOne`, **`@JoinColumn` del lado de Cuota** — la FK vive acá, no en Pago; importante para el orden de borrado), `@Unique(['alumno', 'mes', 'anio'])`.

CRUD en [cuotas.service.ts](backend/src/cuotas/servicios/cuotas.service.ts) / [cuotas.controller.ts](backend/src/cuotas/controladores/cuotas.controller.ts). Permisos: `GET` (listar/detalle) abierto a cualquier autenticado; `POST`/`PATCH`/`DELETE` restringidos a rol `ADMIN` (`RolesGuard` + `@Roles('ADMIN')` por método). `listarTodos` filtra por `alumnoId`/`claseId`/`estado`/`mes`/`anio` vía [filtrar-cuotas.dto.ts](backend/src/cuotas/dtos/filtrar-cuotas.dto.ts) — `claseId` hace join contra `alumno.clase.id` (no existe relación directa Clase↔Cuota, se filtra a través del alumno, mismo criterio que `obtenerUltimaCuotaDeClase`); se agregó para que la pantalla de Clases pueda pedir "todas las cuotas de los alumnos de esta clase" en un solo request. `crear`/`actualizar` validan la constraint `@Unique(['alumno','mes','anio'])` de antemano (`verificarSinDuplicado`) y tiran `BadRequestException` con mensaje claro en vez de dejar que reviente como 500 crudo — mismo estilo que el guard de borrado de `Clase` en uso.

**Alta masiva por clase** — `POST /cuotas/por-clase` ([crear-cuota-por-clase.dto.ts](backend/src/cuotas/dtos/crear-cuota-por-clase.dto.ts), mismo permiso `ADMIN`): en vez de elegir un alumno, se elige una `Clase` y `CuotasService.crearPorClase` crea una `Cuota` individual (mismo mes/monto/vencimiento) para cada alumno de `AlumnosService.listarPorClase(claseId, negocioId)`. Cada alumno sigue teniendo su propia fila de `Cuota` — esto es una acción de alta en lote, no un cambio en el modelo de datos. Si algún alumno ya tenía la cuota de ese mes/año, se lo omite (no se usa `verificarSinDuplicado`, que tira excepción; se usa la variante booleana `existeDuplicado` para no cortar el lote) y se cuenta aparte — la respuesta es `{ creadas, omitidas }`, nunca falla el lote completo por un caso ya cargado. Requirió que `CuotasModule` importe `ClasesModule` (antes solo importaba `AlumnosModule`) — sin ciclo, porque `ClasesModule` no depende de nadie.

`desvincularPago(cuotaId)`: limpia el FK `pago` y repone `estado: PENDIENTE` — lo usa `PagosService.eliminar` **antes** de borrar el `Pago`, porque la FK vive del lado de Cuota (borrar el Pago primero rompe la constraint).

**Subida y revisión de comprobante** — endpoints nuevos bajo `/cuotas/:id/comprobante/...`, todos reutilizando `obtenerPorId(id, negocioId, alumnoIdSesion)` para la autorización (el alumno dueño de la cuota, o cualquier `ADMIN` del negocio):
- `POST solicitar-subida` `{ nombreArchivo, contentType }` (cualquier autenticado dueño de la cuota): arma una key `comprobantes/{negocioId}/{cuotaId}/{timestamp}-{nombreArchivo}` y devuelve `{ url, key }` — la `url` es una PUT prefirmada de `ArchivosService` (ver sección Archivos). `contentType` restringido server-side a `image/jpeg|image/png|application/pdf` vía `@IsIn(...)` en [solicitar-subida-comprobante.dto.ts](backend/src/cuotas/dtos/solicitar-subida-comprobante.dto.ts) — antes de esto, el frontend solo lo insinuaba con `accept=`, sin ninguna validación real.
- `POST confirmar` `{ key }`: `ArchivosService.existe(key)` confirma que el archivo realmente llegó al bucket antes de confiar en el aviso del cliente; si está, `comprobanteUrl = key` y `estado = EN_REVISION`.
- `GET comprobante`: `{ url }` de descarga prefirmada fresca (TTL corto), para *ver* el comprobante — se pide de nuevo cada vez, nunca se guarda una URL pública fija (bucket privado, ver Decisiones).
- `PATCH aprobar` `{ metodo, montoPagado? }` (`ADMIN`): valida `estado === EN_REVISION`, y llama **sin modificarlo** a `PagosService.crear()` (ver abajo) con el `comprobanteUrl` ya guardado — reusa tal cual la regla existente de "crear un Pago marca la Cuota como PAGADA". Devuelve el `Pago` creado, no la `Cuota` (el frontend vuelve a pedir los datos después).
- `PATCH rechazar` (`ADMIN`): limpia `comprobanteUrl` y vuelve a `PENDIENTE` — mismo criterio que `desvincularPago`. **Ojo**: esto siempre borró cualquier rastro del comprobante rechazado (ver sección Comprobantes de abajo, que resuelve exactamente ese hueco).

Esto introdujo una dependencia circular real nueva entre `CuotasModule` y `PagosModule` (antes solo iba en un sentido: Pagos necesita Cuotas para marcarla `PAGADA`/revertirla; ahora Cuotas también necesita `PagosService.crear()` para `aprobar`) — resuelta con `forwardRef()` en ambos módulos y ambas inyecciones, exactamente el mismo mecanismo ya usado para el ciclo Alumnos↔Cuotas.

`confirmarComprobante`/`aprobarComprobante`/`rechazarComprobante` ahora también llaman a `ComprobantesService` (ver sección siguiente) para dejar un registro histórico de cada intento de carga — aditivo, no cambia nada de lo descrito arriba. `eliminar(id, negocioId)` agrega un chequeo previo (`ComprobantesService.tieneHistorial`) que bloquea con `BadRequestException` el borrado de una cuota que ya tuvo comprobantes cargados, porque `Comprobante.cuota` es ahora una FK real (`onDelete: 'RESTRICT'`) — sin este chequeo, ese borrado tiraría un 500 crudo (no hay ningún exception filter global en el proyecto).

### Comprobantes (`backend/src/comprobantes/`)

Módulo nuevo, puramente **aditivo**: registra el historial completo de cada intento de carga de comprobante, algo que antes no existía. El problema de fondo que motivó esto: `CuotasService.rechazarComprobante` siempre limpió `cuota.comprobanteUrl` al rechazar, así que un comprobante rechazado no dejaba ningún rastro en la base (el archivo podía seguir en el bucket, pero nada lo referenciaba) — los aprobados sí sobrevivían para siempre porque se copian a `Pago.comprobanteUrl`. Se le planteó esto al usuario explícitamente (mostrar solo lo rastreable hoy vs. historial completo con rechazados) y eligió historial completo.

`Comprobante` ([comprobante.entity.ts](backend/src/comprobantes/modelo/comprobante.entity.ts)): `id`, `negocio` (NOT NULL), `cuota` (`ManyToOne(() => Cuota, { onDelete: 'RESTRICT' })`, NOT NULL), `key` (string, la key del bucket), `estado: EstadoComprobante` (enum propio — `EN_REVISION`/`APROBADO`/`RECHAZADO`, deliberadamente separado de `EstadoCuota`: el ciclo de vida de un intento de carga no es el mismo que el de la cuota), `fechaCarga`, `fechaRevision?`, `revisadoPor?` (`ManyToOne` a `Usuario`, nullable). Sin columna `nombreArchivo` — el nombre/extensión para mostrar se deriva de `key` al leer, mismo criterio que ya usaba `dashboard-resumen.html`. Una cuota puede acumular **varias** filas con el tiempo (carga → rechazo → nueva carga → aprobación es un flujo real).

`Cuota.comprobanteUrl`/`estado` se dejaron exactamente como estaban a propósito — siguen siendo la señal de "hay algo pendiente ahora mismo" que usan el Portal, `alumno-detalle` y el panel del Dashboard. `Comprobante` es una tabla de auditoría en paralelo, no un reemplazo — cero riesgo de regresión sobre esos flujos ya funcionando.

`ComprobantesService`: `registrarCarga` (inserta una fila `EN_REVISION`, llamado desde `confirmarComprobante`), `marcarRevisado` (busca la fila `EN_REVISION` más reciente de la cuota y la resuelve a `APROBADO`/`RECHAZADO`; si no encuentra ninguna —cuotas que ya estaban `EN_REVISION` antes de este cambio, o un re-envío que dejó un intento anterior huérfano— reconstruye la fila usando la `key` que la `Cuota` todavía tiene en ese momento, en vez de bloquear la revisión real), `tieneHistorial` (para el chequeo de borrado de Cuotas), `listarTodos` (mismo estilo de `where` que `CuotasService.listarTodos`, filtra por `alumnoId`/`claseId`/`estado`/`mes`/`anio` vía [filtrar-comprobantes.dto.ts](backend/src/comprobantes/dtos/filtrar-comprobantes.dto.ts)), `obtenerUrlDescarga` (URL prefirmada fresca vía `ArchivosService.generarUrlDescarga`, mismo criterio que el endpoint equivalente de Cuotas).

`ComprobantesController` (`@Controller('comprobantes')`, guard de clase `ADMIN` — a diferencia de `CuotasController`/`NegociosController` que mezclan público/protegido, acá **todas** las rutas son ADMIN-only porque es una pantalla de auditoría, ningún alumno la usa): `GET /comprobantes` (listado filtrable), `GET /comprobantes/:id/descargar`.

`ComprobantesModule` **no tiene `forwardRef` con `CuotasModule`** — no hay ciclo real (solo `CuotasModule` importa `ComprobantesModule`, dirección única), mismo criterio que `ClasesModule` no necesita importar `AlumnosModule` para que la relación `Alumno.clase` funcione a nivel de TypeORM. Sí importa el repositorio de `Cuota` (`TypeOrmModule.forFeature([Comprobante, Cuota])`) para poder leer `comprobanteUrl` en el caso de reconstrucción de `marcarRevisado` — eso es solo un repositorio, no el módulo completo, así que tampoco genera ciclo.

**Pendiente de backfill**: las cuotas que ya estaban `EN_REVISION` y los pagos ya aprobados de antes de este cambio no tienen fila en `Comprobante` — falta correr un backfill puntual (insertar una fila `EN_REVISION` por cada `Cuota` en ese estado y una `APROBADO` por cada `Pago` con `comprobanteUrl`) antes de considerar el historial completo en producción. Los rechazados de antes de este cambio son irrecuperables por definición.

### Pagos (`backend/src/pagos/`)

`Pago` ([pago.entity.ts](backend/src/pagos/modelo/pago.entity.ts)): `id`, `negocio` (NOT NULL), `cuota` (inverso del `OneToOne`), `metodo: MetodoPago` (enum: `EFECTIVO`, `TRANSFERENCIA`, `TARJETA`, `MERCADOPAGO`), `montoPagado`, `fechaPago`, `comprobanteUrl?` (string simple — desde que existe la subida real, guarda la key del bucket que ya traía la `Cuota` al aprobarse; si un pago se registra a mano sin pasar por el flujo de comprobante, sigue aceptando cualquier string suelto, sin `@IsUrl()`), `registradoPor?` (`ManyToOne` opcional a `Usuario`).

CRUD en [pagos.service.ts](backend/src/pagos/servicios/pagos.service.ts) / [pagos.controller.ts](backend/src/pagos/controladores/pagos.controller.ts). Mismo esquema de permisos que Cuotas. Reglas de negocio:
- Al **crear** un pago: valida que la cuota exista (scopeada por negocio), que no tenga ya un pago (`OneToOne`), y **marca automáticamente la Cuota como `PAGADA`**.
- Al **eliminar** un pago: revierte la Cuota a `PENDIENTE` (vía `desvincularPago`).
- `registradoPor` se toma del JWT (`request.user.sub`) en el controller, **nunca del body** — no se puede falsificar quién registró el pago.
- En las respuestas, `registradoPor` trae `select: { id, email }` únicamente — **fix de seguridad real**: antes devolvía el `Usuario` completo, incluyendo el hash de la contraseña.

### Archivos (`backend/src/archivos/`)

Módulo nuevo, sin controller propio — solo expone `ArchivosService` (usado hoy únicamente por `CuotasService` para el comprobante). Mismo patrón que [`EmailService`](backend/src/auth/services/email.service.ts): inyecta `ConfigService`, arma el cliente en el constructor leyendo `RAILWAY_BUCKET_ENDPOINT/ACCESS_KEY_ID/SECRET_ACCESS_KEY/NAME` (`@aws-sdk/client-s3` + `@aws-sdk/s3-request-presigner`, instalados desde hace tiempo pero sin usar hasta esta vuelta). A diferencia de Email (que cae a loguear por consola si no hay `BREVO_API_KEY`), acá si `RAILWAY_BUCKET_ENDPOINT` no está seteado el cliente queda `null` y cualquier método tira `InternalServerErrorException` — no hay mock razonable para almacenamiento binario, y así el resto del backend arranca sin problema en un entorno sin bucket configurado (falla recién si alguien intenta usarlo).
- `S3Client` con `forcePathStyle: true` — necesario para endpoints S3-compatibles no-AWS como el bucket de Railway.
- `generarUrlSubida(key, contentType)`: PUT prefirmada (~5 min).
- `generarUrlDescarga(key)`: GET prefirmada (~10 min), se pide de nuevo cada vez que hace falta ver un archivo (bucket privado, sin URLs públicas persistidas).
- `existe(key)`: `HeadObjectCommand`, para confirmar que un archivo realmente se subió antes de confiar en el aviso del cliente.
- `descargarObjeto(key)`: `GetObjectCommand` **directo, sin prefirmar** — devuelve el `Body` (stream) tal cual, para el proxy público de logos (ver Negocios). A diferencia de `generarUrlDescarga`, esto no genera una URL para que el navegador la pida después — el backend mismo hace la request a S3 y reenvía el resultado.

### Negocios (`backend/src/negocios/`)

Hasta hace poco era el módulo más chico del proyecto: solo la entidad `Negocio` + `TypeOrmModule.forFeature`, sin service ni controller. Ahora tiene API real tanto para crear un negocio (uso operativo, no self-service) como para que el propio negocio lea/edite sus datos (hoy, solo el logo).

- **`POST /negocios`** — crea un negocio nuevo. **No usa JWT/roles**: no tiene sentido pedir "ADMIN de qué negocio" para crear uno que todavía no existe, y dejarlo abierto a cualquier `ADMIN` ya autenticado sería que el admin de un negocio pudiera crear negocios ajenos, rompiendo el aislamiento multi-tenant. En cambio usa `ApiKeyGuard` ([api-key.guard.ts](backend/src/auth/guards/api-key.guard.ts)): un header `x-api-key` comparado contra la variable de entorno `ADMIN_SETUP_KEY` — pensado para uso manual (curl/Postman/Swagger) de quien administra la plataforma al dar de alta un cliente nuevo, **nunca** llamado desde la app ni expuesto en ninguna pantalla. Si `ADMIN_SETUP_KEY` no está seteada, el guard tira 500 en vez de dejar pasar por error.
- **`POST /negocios/:id/admin`** — mismo `ApiKeyGuard`, mismo espíritu: crea el primer usuario `ADMIN` de un negocio ya existente (`{ email, password, nombre, apellido }`). Es la versión HTTP del script [seed-admin.ts](backend/src/database/seeds/seed-admin.ts) (que sigue existiendo tal cual, para uso por CLI) — vive en `NegociosService.crearAdmin()`, que para no depender de `AuthService` (evitaría un ciclo: `AuthModule` ya importa `NegociosModule`) usa `UsuarioService` directo, importando `UsuariosModule` en `NegociosModule` (sin riesgo de ciclo, `UsuariosModule` es standalone). Valida que el negocio exista y que el rol `ADMIN` exista (mismos mensajes de error que el script), y la respuesta nunca incluye el hash de la password (mismo criterio de siempre — se arma con `const { password, ...resto } = guardado`).
- `GET /negocios/actual` (cualquier autenticado, `ADMIN` o `ALUMNO` — lo necesita el Portal): devuelve `{ id, nombre, logoUrl }`, con `logoUrl` ya armado como URL completa y lista para usar en un `<img src>` (o `null` si no hay logo cargado) — el frontend nunca ve la key del bucket.
- `POST /negocios/actual/logo/solicitar-subida` / `.../confirmar` (`ADMIN`): mismo patrón exacto que el flujo de comprobante de Cuotas (key `logos/{negocioId}/{timestamp}-{nombreArchivo}`, `ArchivosService.existe()` antes de confirmar). `contentType` restringido a `image/jpeg|png|svg+xml|webp`.
- `DELETE /negocios/actual/logo` (`ADMIN`): limpia el logo (acción compañera de subir, por si se carga algo por error).
- **`GET /negocios/:id/logo` — público, sin ningún guard.** Es la pieza clave de la estrategia: en vez de intentar que el bucket sirva el objeto directo (privado a propósito, y sin certeza de que el bucket real de Railway soporte ACLs/policies públicas — todavía no hay credenciales reales, ver Pendientes), el backend mismo hace de proxy: pide el objeto con `ArchivosService.descargarObjeto()` (sus propias credenciales, siempre válidas) y lo pipea directo en la respuesta (`@Res()` + `body.pipe(res)`, primer uso de `@Res()` en el proyecto). La URL resultante (`https://.../negocios/5/logo`) **no vence nunca** — a diferencia de las URLs prefirmadas de comprobante (10 min), esto es justo lo que hace falta para un `<img>` embebido en un mail que se puede abrir días después. **Ojo con el `Cache-Control`**: al ser siempre la misma URL para un negocio, cachearla fuerte (`max-age` largo, lo que tenía al principio) hace que el navegador siga mostrando el logo viejo un buen rato después de reemplazarlo o borrarlo, aunque `GET /negocios/actual` ya refleje el cambio al instante — se dejó en `no-cache` (siempre revalida) a propósito, para que un cambio de logo se vea reflejado enseguida en vez de quedar pegado hasta que venza el cache.
- `NegociosController` no tiene guard a nivel de clase (mismo criterio que `AuthController`, que también mezcla endpoints públicos y protegidos) — cada método declara el suyo.
- Nueva env var **`BACKEND_URL`** (mismo espíritu que `FRONTEND_URL`) — la usa `NegociosService.construirUrlLogo()` para armar la URL absoluta del proxy. Hay que setearla también en Railway.

### Auth (`backend/src/auth/`)

- [auth.service.ts](backend/src/auth/services/auth.service.ts): `register(dto, negocioId)`, `validateUser` (compara password con bcrypt, usado por `LocalStrategy`), `login(user)` (arma el JWT con `sub`, `email`, `negocioId`, `alumnoId`, `roles` y `permissions` aplanados sin duplicados; devuelve también `ruta: '/portal'` o `'/dashboard'` según si el usuario tiene el rol `ALUMNO` — el controller ya hacía `{ ruta: '/dashboard', ...loginResponse }`, así que alcanzó con sumar `ruta` a lo que devuelve `login()`, el spread existente la pisa sin tocar el controller).
- **Invitación de alumno al portal** (reemplaza la idea original de registrar el `Usuario` a mano con un `alumnoId`): desde Alumno Detalle, el admin dispara "Invitar a crear cuenta" (solo visible si el alumno tiene `email` y no tiene `usuario` vinculado todavía) → `POST /auth/invitar-alumno` (`ADMIN`) → `AuthService.generarInvitacion` valida el alumno, firma un JWT de invitación stateless (`{ tipo: 'invitacion_alumno', alumnoId, negocioId }`, `expiresIn: '48h'`, mismo `JwtService` que ya usa el login, sin tabla nueva), pide `NegociosService.obtenerActualConLogo(negocioId)` y llama a `EmailService.enviarInvitacionAlumno` pasándole el `logoUrl` (si el negocio tiene uno cargado, el mail lo antepone como `<img>`; si no, el mail sale igual que antes — sin ícono de imagen rota). Esto sumó `NegociosModule` a los imports de `AuthModule` (sin ciclo, Negocios no depende de Auth). El alumno abre el link (`{FRONTEND_URL}/completar-registro?token=...`), define su contraseña, y ahí recién se crea el `Usuario` (`POST /auth/completar-invitacion`, **público**, sin guard) — `AuthService.completarInvitacion` verifica el token, crea el `Usuario` con rol `ALUMNO` y lo vincula al `Alumno` (`AlumnosService.vincularUsuario`, cross-tenant-safe, reusa `obtenerPorId`; falla si el alumno ya tenía usuario vinculado).
- **`PayloadInvitacionAlumno` suma `email`**: el JWT de invitación (`{ tipo, alumnoId, negocioId }`) ahora incluye también `email: alumno.email` — no cambia nada del lado del backend (`completarInvitacion` sigue resolviendo el email real desde `AlumnosService.obtenerPorId`, no confía en el del token para crear el `Usuario`), es puramente para que `CompletarRegistro` (frontend) pueda mostrarlo de forma **no editable** en la pantalla, con la aclaración "vas a usar este correo para iniciar sesión" — mismo patrón ya usado por `AuthService` del frontend para leer `negocioId`/`roles` del JWT de sesión (`JSON.parse(atob(payload))`, sin librería). Invitaciones ya enviadas antes de este cambio siguen siendo válidas (el JWT sigue verificando igual), simplemente no traen `email` en el payload — el frontend lo maneja mostrando el formulario sin ese campo en vez de romper.
- [email.service.ts](backend/src/auth/services/email.service.ts): manda las invitaciones por la **API HTTP de Brevo** (`POST https://api.brevo.com/v3/smtp/email`, `fetch` nativo, sin SDK — solo necesita `BREVO_API_KEY` + `SMTP_FROM` como remitente). **No siempre fue así**: originalmente usaba Nodemailer + SMTP genérico (`SMTP_HOST/PORT/USER/PASSWORD`), pero en producción (Railway) el `POST /auth/invitar-alumno` tiraba `Connection timeout` — se armó un diagnóstico temporal (`net.createConnection` contra Brevo en los puertos 587 y 465 *y* contra `smtp.gmail.com:587` como control) que confirmó que **Railway bloquea las conexiones salientes por SMTP en general** (los tres intentos fallaron, cambiar de puerto no cambió nada) — no era un problema de credenciales, de `secure`/TLS, ni de Brevo bloqueando la IP. La solución de fondo fue dejar de usar SMTP directo y hablar por HTTPS puerto 443, que nunca está bloqueado. `SMTP_HOST/PORT/USER/PASSWORD` quedaron en `.env` sin usar (por si el bloqueo de Railway se levanta algún día) y `nodemailer`/`@types/nodemailer` se sacaron de `package.json` por completo. Si `BREVO_API_KEY` no está seteada, **loguea el link de invitación por consola en vez de enviarlo** (mismo fallback de siempre) — permite probar todo el flujo en desarrollo sin depender de Brevo.
- `AlumnosService.listarTodos`/`obtenerPorId` ahora suman `usuario: true` a `relations` con `select: { usuario: { id: true } }` (mismo patrón que `registradoPor` en Pagos) — exponen si el alumno ya tiene cuenta sin filtrar el hash de password.
- `LocalStrategy`/`JwtStrategy`: login por email+password y validación de bearer token.
- `RolesGuard`/`PermissionsGuard` + `@Roles(...)`/`@Permissions(...)`: autorización basada en el payload del JWT (`user.roles[].name`, `user.permissions[]`). No tienen ninguna noción de negocio — el aislamiento entre negocios depende 100% del filtrado por `negocioId` en los services, no de los roles (un "ADMIN" del Negocio A tiene el mismo nivel nominal que uno del Negocio B).
- **`@AlumnoIdSesion()`** ([alumno-id-sesion.decorator.ts](backend/src/auth/decorators/alumno-id-sesion.decorator.ts), mismo patrón que `@NegocioId()`): lee `request.user.alumnoId` (`null` para cuentas staff/ADMIN). Cierra el hueco que quedaba después de habilitar logins de `ALUMNO`: antes, `GET /alumnos`, `GET /cuotas` y `GET /pagos` estaban abiertos a "cualquier autenticado" sin mirar el rol, así que una cuenta `ALUMNO` podía pedirlos directo (sin pasar por la UI) y ver el padrón/cuotas/pagos completos del negocio. Ahora `AlumnosService`/`CuotasService`/`PagosService` reciben un `alumnoIdSesion?: number | null` opcional en `listarTodos`/`obtenerPorId`: si no es `null`, `listarTodos` se recorta a ese alumno (y en Cuotas/Pagos **pisa** cualquier `?alumnoId=` que venga por query, no lo combina) y `obtenerPorId` tira `NotFoundException` si el recurso no es del alumno de la sesión — mismo criterio de "nunca `Forbidden`" que ya usa el resto del código para no filtrar existencia entre negocios. Las mutaciones de Cuotas/Pagos/Clases ya estaban bien (`RolesGuard` + `@Roles('ADMIN')`); las de **Alumnos no** (hueco real, ver sección Alumnos) — corregido en la misma vuelta que el guard de navegación del frontend. `GET /clases` quedó afuera a propósito (no es sensible, el Portal ni lo consulta).
- `AuthController`: `POST /auth/register` (`@Roles('ADMIN')` + `@NegocioId()`, sigue igual para altas de staff), `POST /auth/login`, `POST /auth/invitar-alumno` (`ADMIN`), `POST /auth/completar-invitacion` (público).

## Frontend (`frontend/`)

Implementa las 6 pantallas de un design handoff (dashboard en 3 variantes, listado/detalle de alumnos, portal de alumno mobile). Desde esta etapa, **Auth/Alumnos/Cuotas/Clases hablan con el backend real**; el flujo de comprobante/revisión de Pagos sigue mockeado (ver Pendientes).

- **Tailwind**: tokens de diseño (colores OKLCH, tipografías Plus Jakarta Sans/Inter) en `src/styles.scss` vía `@theme`. Locale `es-AR` registrado en `app.config.ts` para que los `DatePipe` salgan en español.
- **Auth** (`core/services/auth.service.ts`, `core/guards/auth.guard.ts`, `core/guards/admin.guard.ts`, `core/interceptors/auth.interceptor.ts`, `features/auth/login/`): `login(email, password)` pega a `POST /auth/login`, guarda el `accessToken` en `localStorage` y decodifica el payload del JWT en el cliente (`JSON.parse(atob(...))`, sin librería nueva) para exponer `usuario` (signal) con `negocioId`/`roles`/`permissions`. El interceptor agrega el `Bearer` a cada request y, ante un `401`, hace `logout()` + redirige a `/login`. `authGuard` solo exige sesión iniciada (usado en `/portal`). `adminGuard` (`AuthService.esAlumno()`, chequea `roles` por nombre) además redirige a `/portal` si la sesión es de un `ALUMNO` — usado en `/dashboard`, `/alumnos`, `/clases`, `/cuotas`: antes de esto, un `ALUMNO` logueado podía navegar manualmente a esas rutas (la data ya venía scopeada/bloqueada por el backend gracias a `@AlumnoIdSesion()` y los `@Roles('ADMIN')`, pero la pantalla igual se rompía o quedaba vacía en vez de mandarlo directo al Portal).
- **Modelos** (`core/models/`): `Alumno`/`Cuota`/`Clase`/`Pago` ya reflejan la forma real del backend (`claseId`/`clase` opcionales — no todo alumno tiene clase asignada; `Cuota` suma `comprobanteUrl?`; `Pago` es `id`/`cuotaId`/`metodo`/`montoPagado`/`fechaPago`/`comprobanteUrl?`, alineado con la entidad real). `EstadoCuota.EN_REVISION` ya es un estado real que puede venir del backend (antes era exclusivo del frontend, ver Decisiones/Pendientes resueltos).
- **Servicios** (`core/services/`): `AlumnosService`/`CuotasService`/`ClasesService`/`PagosService` usan `HttpClient` contra `environment.apiUrl` (conversión manual de fechas string→`Date`, porque `HttpClient` no lo hace solo). `AlumnosService.crear()` postea al backend real (usado por el alta de alumnos, ver más abajo). `PagosService.listarPorCuotas(cuotaIds)` es real: como el backend solo filtra `GET /pagos` por un `cuotaId` a la vez, pide uno por cuota en paralelo con `forkJoin` y aplana el resultado (mismo patrón que `AlumnosService.componerConEstado`).
- **Subida real de comprobante** (`CuotasService.subirComprobante(cuotaId, archivo)`): reemplazó por completo el mock en memoria (`cuotasEnRevision`/`marcarEnRevision`) que existía antes — ahora `EN_REVISION` es un estado real que viene del backend. Orquesta 3 pasos: `POST solicitar-subida` → `PUT` directo al bucket → `POST confirmar`. **El PUT al bucket usa `fetch()` nativo, no `HttpClient`** — el [`authInterceptor`](frontend/src/app/core/interceptors/auth.interceptor.ts) le suma el `Authorization: Bearer` de la app a *cualquier* request de `HttpClient` sin filtrar por URL, lo que rompería la firma de la URL prefirmada si viajara por ahí. `verComprobante(cuotaId)` pide una URL de descarga prefirmada fresca cada vez (se abre en pestaña nueva, no se persiste). `aprobarComprobante`/`rechazarComprobante` (`ADMIN`) llaman a los endpoints homónimos del backend — ojo que `aprobarComprobante` devuelve `void` a propósito: el backend responde con el `Pago` creado, no la `Cuota`, así que quien lo llama tiene que volver a pedir los datos para reflejar el `PAGADA`. `listarEnRevision()` pasó de filtrar un array mockeado a ser simplemente `listarTodos({ estado: EstadoCuota.EN_REVISION })` (el filtro `estado` ya existía).
- **Comprobantes** (`features/comprobantes/comprobantes-list`, ruta `/comprobantes` — el ítem del nav que antes estaba deshabilitado, `route: null`, ahora apunta acá): pantalla de solo lectura, sin modal de alta/edición (un `Comprobante` se crea únicamente por el flujo de subida, nunca a mano). Mismo patrón de señales/filtros/tabla que `cuotas-list` (filtros por alumno/clase/estado/mes/año, `aplicarFiltros`/`limpiarFiltros` re-disparando `cargar()`, sin paginación). Nuevo `ComprobantesService` (`core/services/comprobantes.service.ts`): `listarTodos(filtros)` y `verComprobante(id)` (pide `{url}` a `GET /comprobantes/:id/descargar` y abre `window.open`, mismo patrón que `CuotasService.verComprobante`). Estados con `app-status-badge`: `APROBADO`→`ok`, `RECHAZADO`→`debt`, `EN_REVISION`→`soon` — reutiliza los 3 tonos existentes, no hace falta un 4to. A propósito **no** duplica las acciones de aprobar/rechazar — esas siguen viviendo únicamente en `alumno-detalle`; esta pantalla es de consulta/historial.
- **Alta de Alumno** (`features/alumnos/alumnos-list`): botón "+ Nuevo alumno" abre un modal (nombre/apellido obligatorios, email/teléfono/clase opcionales) y llama a `AlumnosService.crear()`; al guardar recarga el listado. El `negocioId` nunca viaja en el form, lo resuelve el backend desde el JWT.

Se sumó `AlumnosService.cambiarEstado(id, activo)` (`PATCH /alumnos/:id`, el mismo endpoint de edición) y una columna "Acciones" en la tabla. Un alumno activo tiene un botón "Dar de baja" (modal de confirmación propio, con lenguaje explícitamente **no** destructivo — "podés reactivarlo cuando quieras" — a diferencia de los modales de borrado de Clase/Cuota que sí son irreversibles). El alta de Cuota no expone el campo `estado` (nace `PENDIENTE` siempre, como hace el backend por default); el campo solo aparece al editar. El modal de alta (no el de edición) tiene un selector "Un alumno" / "Toda una clase": por clase reemplaza el select de Alumno por uno de Clase y llama a `CuotasService.crearPorClase()`, que crea una cuota por cada alumno de esa clase; el resultado se muestra en un banner descartable arriba de la tabla ("Se crearon N cuotas nuevas" + cuántas se omitieron por ya existir, si aplica) — nada de `alert()`.

Al cargar la lista, `ClasesList` pide en paralelo (`forkJoin`) `CuotasService.listarTodos({ claseId })` por cada clase — mismo patrón de fetch-paralelo que ya usa `PagosService.listarPorCuotas` — y agrupa el resultado del lado del cliente por `(anio, mes, monto)`, contando cuántas cuotas de ese grupo están `PAGADA`/`PENDIENTE`/`VENCIDA`/`EN_REVISION`. El nav lateral "Clases" apunta a `/clases` (gestión del catálogo) — antes apuntaba a `/dashboard/clases`, que sigue existiendo como tab del Dashboard (vista operativa de alumnos agrupados por clase, no se tocó). Reutiliza `app-status-badge` (mismo componente de `cuotas-list`) para los cuatro estados de cuota, con los mismos tonos reales que usa `CuotasList.badgeTone()` (`PENDIENTE`/`EN_REVISION` ambos `soon`, no se inventó un tono nuevo para "en revisión"). Nació primero como un documento externo (Artifact) pedido para compartir con administradores; se decidió traerlo adentro de la app para que quede versionado junto con el producto y no se desactualice por separado.

Recién al click en "Guardar cambios" corre `subirLogo()` de verdad; si falla, la preview y la selección se mantienen para reintentar sin tener que volver a elegir el archivo. "Quitar imagen" es una acción con dos comportamientos según el estado: si hay una selección todavía no guardada, cancela sin pegarle al backend (nada que borrar); si no hay selección pendiente y hay un logo ya guardado, ahí sí llama a `eliminarLogo()` (DELETE real). Los dos botones ("Quitar imagen", "Guardar cambios") solo aparecen si hay algo para mostrar (logo guardado o preview pendiente), alineados a la derecha debajo de la imagen, en ese orden.
- **Portal del Alumno** (`features/portal/portal-alumno`, ruta `/portal`, ahora protegida con `authGuard`): el layout base es una tarjeta mobile (`max-w-md`, calco del design handoff original que era "mobile-only") — desde esta vuelta suma un layout de escritorio real a partir de `lg:` (1024px): banner de header a todo el ancho, y debajo un grid de 2 columnas (`lg:grid-cols-2`) con la cuota actual + upload de comprobante a la izquierda y el historial de pagos (envuelto en su propia card a partir de `lg:`) a la derecha, todo centrado en `lg:max-w-5xl`. Por debajo de `lg:` el markup no cambió — sigue siendo exactamente la tarjeta mobile de antes (verificado con Playwright en 390px vs 1440px, sin regresión). Suma botón "Cerrar sesión" (`salir()`, mismo patrón que `AdminShell`) en el header, y también en el estado vacío `sinAlumnoVinculado` (antes esa pantalla no tenía ninguna forma de salir). Usa datos reales de Alumno/Cuota/Pago, y desde esta etapa el `alumnoId` sale del JWT (`authService.usuario()?.alumnoId`) en vez de estar hardcodeado — si el usuario logueado no tiene ningún alumno vinculado, se muestra un estado vacío en vez de romper. Cuota actual con detalle (si está `PAGADA`, muestra método y fecha de pago del `Pago` real correspondiente, buscado entre los ya cargados por `cuotaId`); si está `EN_REVISION` se reemplaza el bloque de upload por un mensaje ("Estamos revisando tu comprobante") en vez de seguir ofreciendo subir de nuevo. "Historial de pagos" (antes listaba cuotas con un badge "Pagada" fijo — bug corregido) ahora es una lista real de `Pago[]` ordenada por `fechaPago` desc, cruzando cada pago con su cuota (por `cuotaId`) para mostrar mes/año. La subida de comprobante ahora es real (`CuotasService.subirComprobante`, ver sección Servicios) con estados `subiendoComprobante`/`errorComprobante` para no fingir éxito si el bucket rechaza el archivo o no está configurado. `AlumnoDetalle` comparte el ajuste de datos reales (su panel "Comprobantes cargados" pasó a llamarse "Pagos registrados"), suma el botón "Invitar a crear cuenta" (visible solo si el alumno tiene email y no tiene usuario vinculado), y **ya no tiene** el botón "Cargar comprobante" que antes duplicaba el mock del Portal — subir el comprobante es acción del alumno, no del admin. En su lugar, cuando una cuota de la lista está `EN_REVISION`, aparecen tres acciones inline: "Ver comprobante" (abre la URL de descarga prefirmada en pestaña nueva), "Aprobar" (modal con selector de método + monto prefijado con el de la cuota) y "Rechazar" (modal de confirmación, mismo patrón que el borrado de Clase) — cierra el flujo al que ya apuntaba el panel "Comprobantes por revisar" del Dashboard (antes llevaba a un callejón sin salida). De paso se corrigió que ese panel del Dashboard **inventaba** un nombre de archivo falso (`comprobante_${nombre}.jpg`) para mostrar la extensión — ahora usa la key real de `comprobanteUrl`. El Portal también suma el logo institucional (si el negocio tiene uno cargado) arriba del saludo, en el banner — pedido a `NegociosService.obtenerActual()` al cargar; si no hay logo, el banner queda exactamente igual que antes.

**Color personalizable del Portal** (`core/services/preferencias.service.ts`, nuevo): el alumno puede elegir cualquier color desde un `<input type="color">` nativo en el header del Portal (sin librerías nuevas, mismo criterio de siempre) — el color se aplica al instante (optimista: se actualiza el signal y se dispara el `PATCH` en paralelo, sin esperar confirmación ni mostrar loading, coherente con que es una preferencia cosmética de bajo riesgo) y se persiste en el backend (`GET/PATCH/DELETE /usuarios/mi-color`, ver sección Usuarios). Default `#FB923C` (naranja claro, constante `COLOR_ACCENTO_DEFAULT`) si el usuario no eligió ninguno todavía. Un botón "↺" para restablecer aparece solo cuando el color actual difiere del default.

Técnicamente, el color se aplica pisando las 3 variables CSS (`--color-accent`, `--color-accent-hover`, `--color-accent-soft`) directamente en el `<div>` raíz del componente vía binding de Angular a propiedades custom (`[style.--color-accent]="..."`) — como son variables CSS, heredan a todos los descendientes del Portal sin tocar el resto de la app (el `AdminShell` es un árbol de componentes completamente separado). `accent-hover`/`accent-soft` no se calculan a mano en TypeScript: se arman como expresiones `color-mix(in srgb, {color} X%, black|white)` que el propio navegador resuelve — evita sumar conversión de espacios de color (hex→HSL/OKLCH) en JS para algo que CSS ya sabe hacer nativo. Requirió una normalización global mínima en [styles.scss](frontend/src/styles.scss) para que `input[type="color"]` se vea como un círculo prolijo en todos los navegadores (por default trae un cuadrado con relleno).

- **Bug de fechas corregido (off-by-one por timezone)**: toda fecha-solo que viene del backend como ISO UTC medianoche (`fechaVencimiento`, `fechaAlta`, `fechaPago`) se mostraba un día antes en cualquier timezone negativo (ej. Argentina, UTC-3), porque el pipe `date` de Angular formatea en la zona horaria local del navegador por defecto. Se fuerza `:'UTC'` como tercer parámetro del pipe en todos esos casos (`cuotas-list`, `alumnos-list`, `alumno-detalle`, `portal-alumno`). El mismo bug también aparece si se formatea una fecha "a mano" con `Date.prototype.getDate()`/`getMonth()` en vez de `getUTCDate()`/`getUTCMonth()` — pasó en `AlumnoDetalle.formatearFecha()`, que también hubo que corregir. **Ojo**: esto no aplica a fechas construidas en el cliente con el constructor local de `Date` (ej. `fechaMes()` en `cuotas-list.ts`, que arma `new Date(anio, mes - 1)`) ni a `Date.now()`/`new Date()` reales (ej. el "hoy" del Dashboard) — forzar `:'UTC'`/`getUTC*` ahí introduciría el bug al revés. Cualquier fecha nueva que se agregue mostrando algo que viene del backend tiene que revisarse contra este mismo patrón.
- **Environments** (`src/environments/`): `development`/`staging`/`production`, cada uno con su `apiUrl` (dev apunta a `http://localhost:3000`; staging/production tienen placeholders `TODO-completar-url-...`). Configurados en `angular.json` (`fileReplacements`) + scripts `start:staging`/`build:staging` en `package.json`.

## Decisiones tomadas

- IDs numéricos autoincrementales en todas las entidades (no UUID).
- Multi-tenancy: una sola DB + columna `negocio`, sin RLS (ver sección dedicada arriba).
- `Rol`/`Permiso` globales, no por negocio.
- `Usuario.email` único **globalmente**, no por negocio — el login (`findByEmail`) se ejecuta sin ningún selector de negocio previo, así que un email único por negocio volvería el login ambiguo (requeriría rediseñar el flujo completo para pedir el negocio antes que las credenciales).
- Tipos "catálogo" con reglas de negocio simples (`EstadoCuota`, `MetodoPago`) → enums de TypeScript.
- Tipos "configurables en runtime" (`Rol`, `Permiso`, `Negocio`) → entidades propias con tabla en la base.
- Relaciones muchos-a-muchos (`Usuario↔Rol`, `Rol↔Permiso`) → `@ManyToMany` + `@JoinTable` simple, sin entidad intermedia explícita.
- Frontend: Tailwind CSS (no Angular Material) para poder calzar el diseño custom del handoff; mock services antes que HttpClient real, ya que el backend no exponía CRUDs todavía cuando se armó el frontend.
- `Clase`: se construyó como entidad real en el backend (tenant-scoped, igual que Alumno/Cuota/Pago) en vez de dejarla decorativa o sacarla de la UI — decisión explícita del usuario al notar que el backend no tenía ningún concepto equivalente.
- JWT del frontend: se guarda en `localStorage` (no `sessionStorage`, no cookie httpOnly) por simplicidad en esta etapa — tradeoff de XSS conocido y no resuelto, ver Pendientes.
- ~~Flujo de comprobante/revisión (upload de pago por el alumno, `EstadoCuota.EN_REVISION`): queda deliberadamente fuera de esta conexión frontend-backend... Sigue 100% mockeado en el frontend.~~ — **construido** (subida real a bucket + aprobación/rechazo del admin, ver secciones Cuotas/Archivos/Frontend).
- Alta de cuenta para un Alumno: por **invitación vía email**, no por registro manual del admin — el admin dispara el envío desde Alumno Detalle, el `Usuario` recién se crea cuando el alumno confirma su contraseña por el link. Envío por la **API HTTP de Brevo** (decisión revisada: se había arrancado con Nodemailer + SMTP genérico, pero Railway bloquea SMTP saliente — ver sección Auth para el diagnóstico), con fallback a loguear el link por consola si no está configurado. Token de invitación **stateless** (JWT firmado con el mismo `JwtService`, sin tabla nueva). Disparo **manual** (botón), no automático al crear el alumno.
- Subida de comprobante: **URL prefirmada** (el bucket de Railway, S3-compatible), no proxy a través del backend — el cliente sube el archivo directo, Nest nunca ve los bytes. El bucket queda **privado**: `comprobanteUrl` (en `Cuota` y `Pago`) guarda la **key** del objeto, no una URL pública; para ver un comprobante siempre se pide una URL de descarga prefirmada al momento, de corta duración. Se construyó también la **aprobación/rechazo del admin** en la misma vuelta (no se difirió) — de lo contrario una cuota `EN_REVISION` quedaba trabada sin ninguna forma de resolverla desde la UI, ya que tampoco existe (todavía) una pantalla general de "registrar pago".

## Pendientes / deuda técnica conocida

- **`BREVO_API_KEY` hay que setearla en las variables del servicio del backend en Railway** (no alcanza con el `.env` local, igual que pasó con `CORS_ORIGINS`) — sin ella, las invitaciones se loguean por consola en producción en vez de mandarse.
- **`BACKEND_URL` también hay que setearla en Railway** (mismo motivo) — la usa `NegociosService` para armar la URL pública del logo (`.../negocios/:id/logo`) que va en el mail de invitación y en el Portal. Sin ella, cae al default `http://localhost:3000`, que en producción apuntaría mal.
- **`ADMIN_SETUP_KEY` también hay que setearla en Railway** (mismo motivo) para poder usar `POST /negocios` en producción — sin ella, `ApiKeyGuard` tira 500 en vez de dejar pasar. Elegir una clave real (no la de desarrollo) y guardarla en un lugar seguro, ya que es lo único que protege el alta de negocios.
- **El logo no se probó de punta a punta con el bucket real** (mismo motivo que el comprobante — sin `RAILWAY_BUCKET_*` reales, `solicitar-subida` da un 500 controlado). Sí se verificó todo el resto: guards, validación de `contentType`, el 404 del proxy público sin logo cargado, y que el `<img>` no rompe nada ni en Configuración ni en el Portal cuando la imagen no llega a cargar.
- **Bucket de Railway sin credenciales reales todavía** — `RAILWAY_BUCKET_*` en `.env` están vacías, así que la subida/descarga real de comprobantes no se probó de punta a punta (sí se verificó todo lo demás: guards, validación, la aprobación/rechazo del admin con datos sembrados a mano). Falta completar esas 4 variables con un bucket real y probar el PUT/GET prefirmado en el navegador.
- **Falta backfill de `Comprobante` para datos existentes** — las cuotas que ya estaban `EN_REVISION` y los pagos ya aprobados de antes de agregar este módulo no tienen fila en `Comprobante` (ver sección Comprobantes). Correr un backfill puntual antes de confiar en que el historial está completo en producción.
- ~~Alta de Alumno, y CRUD completo de Clase y Cuota ya tienen UI. Sigue faltando: edición/baja de Alumno desde la UI.~~ — **baja lógica resuelta** (ver sección Frontend). Sigue faltando solo la **edición** de datos de un Alumno ya existente (nombre/apellido/email/teléfono/clase) desde la UI — hoy `ActualizarAlumnoDto` lo soporta todo en el backend, pero no hay ningún formulario de edición en el frontend, solo el toggle de `activo`.
- **Sin pantalla general de registro de pagos "a mano" para el admin** — el CRUD de `Pago` (`POST /pagos`) sigue sin ninguna pantalla equivalente; lo único que existe del lado UI es aprobar/rechazar un comprobante ya subido por el alumno (Alumno Detalle), no cargar un pago desde cero sin que haya un comprobante de por medio.
- **JWT en `localStorage`** — decisión consciente por simplicidad en esta etapa, pero es vulnerable a robo de token vía XSS (a diferencia de una cookie `httpOnly`). Revisar si se justifica migrar antes de exponer esto fuera de un entorno de desarrollo.
- ~~Los `GET` no distinguen `ADMIN` de `ALUMNO`~~ — **corregido** (`@AlumnoIdSesion()`, ver sección Auth). `GET /clases` quedó deliberadamente sin scopear (no expone nada sensible).
- **Sin reenvío/listado de invitaciones pendientes** — si el link de invitación vence (48hs) o se pierde, la única forma de generar uno nuevo es volver a apretar "Invitar" sobre el mismo alumno (funciona porque sigue sin `usuario` vinculado), no hay un endpoint ni pantalla dedicados a "reenviar".
- **Sin Postgres Row-Level Security** — decisión consciente, pero significa que no hay ningún backstop a nivel DB si algún query nuevo se olvida el filtro por `negocioId`. Cualquier código nuevo que toque Alumnos/Cuotas/Pagos tiene que seguir el mismo patrón de scoping.
- **Sin tests automatizados de aislamiento cross-tenant** — el chequeo que se hizo fue manual (ver arriba). Sería el candidato ideal para el primer test e2e real del proyecto, justamente porque es la única red de seguridad que existe.
- `UsuarioService.findByRol`/`findByRolWithoutUser` usan `role.name` en un query builder crudo, pero la columna real es `nombre` — mismo bug que ya se corrigió una vez en otro lado (`findByName`), no se tocó acá todavía.
- ~~`RegistrarUsuarioDto` tiene campos `nombre`/`apellido` que `AuthService.register()` nunca usa~~ — **corregido**: se agregaron `nombre`/`apellido` como columnas reales de `Usuario` (ver sección Usuarios) y `register()` ya los persiste. No hacía falta vincular ningún `Alumno` — `register()` es para altas de *staff* (ADMIN y similares), no de alumnos; esos siguen entrando únicamente por la invitación por email.
- Si se llega a borrar una `Cuota` que todavía tiene un `Pago` asociado, hoy no hay validación que lo impida ni cascada que lo limpie — queda un `Pago` huérfano (`PagosService.eliminar` tiene un guard defensivo para no romper en ese caso, pero el gap de fondo sigue sin resolver).
- **`AlumnosService.eliminar` no valida si el alumno tiene `Cuota`s asociadas** — encontrado al limpiar datos de prueba: borrar un alumno con cuotas tira un 500 crudo (constraint de FK), no un error prolijo tipo `BadRequestException`. Mismo tipo de gap que ya se corrigió para borrar una `Clase` en uso; no se tocó acá todavía.
- No hay migraciones de TypeORM — se depende de `synchronize: true`, a sacar antes de producción (y recién ahí hay que preocuparse por backfills reales en vez de recrear el schema).
- `AuthController.login` documenta en Swagger un body con `nombre`/`apellido` que en realidad no usa (`login` solo lee `email`/`password`).
